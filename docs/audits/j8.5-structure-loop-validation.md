# J8.5 — End-to-End Structure Loop Validation

**Type:** validation only (no architecture, no new slice). **Environment:** dev.
**Date basis:** main @ `dabb49f` (J8 merged via #607).

## 1. Executive summary

The structure migration loop — **Blob write → PG mirror → sync-check → admin PG
read → Phil PG read** — was exercised end-to-end against the dev project with all
three flags enabled **in the validation process only**. On a faithful, active job
the full loop **PASSED**: a real reversible edit landed in Blob, the mirror wrote
it to Postgres, the admin and Phil overlays both served the edit **from Postgres**
(no fallback, no cross-worker leakage), the edit reverted cleanly, and a simulated
PG outage fell back to Blob with no user-visible failure. Production stays inert
(flags OFF by default, no `SUPABASE_DB_URL` in prod).

**One material finding** the validation surfaced (its purpose): the read overlays
use an **order-sensitive, byte-identical** parity gate, so **legacy jobs whose
Blob shape is non-normalized** (sparse area records and/or array order ≠ PG
`sort_order`) **conservatively fall back to Blob even though their data is in sync**
(the importer-projection sync-check is IN SYNC for them). The dual-write cannot
change this — the data already matches; the difference is *representation*. So
today **most existing Phil-visible jobs are Blob-served, not PG-served**, and will
remain so until re-saved through the builder (which normalizes shape) or until the
read parity is deliberately relaxed (which would trade away the byte-identical
guarantee). New jobs and builder-edited jobs **are** PG-served.

**J9 readiness: CONDITIONAL** (see §13).

## 12. Findings

1. **The loop works end-to-end and is safe.** For a faithful/normalized job, every
   rung passed: Blob → mirror → sync → admin PG read → Phil PG read → revert →
   fallback. Best-effort, idempotent (re-mirror = 0 rows), no leakage, production
   inert.
2. **Read overlays are conservatively Blob-serving for legacy-shaped jobs (by
   design).** The three real Phil-visible jobs are **not** byte-faithful to the PG
   reconstruction (sparse Blob area records missing `spaceType/order/archived/task
   lists`, and/or Blob array order ≠ PG `sort_order`), so the order-sensitive
   parity gate falls back to Blob. Their **data is in sync** (importer-projection
   sync-check IN SYNC) — the mismatch is representational.
3. **The dual-write cannot fix finding 2** — it is idempotent against already-synced
   data (mirroring those jobs writes 0 rows; PG stays 240==240, no orphans). The
   only ways to make them PG-served are (a) re-save them through the builder
   (writes a normalized shape), or (b) relax the read parity to the importer-
   projection equivalence (which would forfeit the byte-identical-output guarantee
   that J6/J7 deliberately hold).
4. **No corruption, no orphan rows.** Mirroring faithful and legacy jobs repeatedly
   left PG at the exact pre-J8.5 baseline (240 entities, identical hash).
5. **Cross-process sync-check timing artifact** (harness only): a separate-process
   sync-check immediately after a Blob write can read a stale CDN copy. The live
   mirror path is same-process (read-after-write consistent), so this does not
   affect production.

## 13. Risks

- **Coverage risk (not safety):** with the read flags on in production today, most
  *existing* jobs would still be served from Blob (finding 2). PG-read value grows
  incrementally as jobs are edited (each builder save normalizes + mirrors →
  faithful). A one-off normalization/re-import pass would accelerate coverage.
- **J9 inherits the same gate:** task-instance/status dual-write + a future task
  read would use the same conservative parity, so the same legacy jobs would fall
  back — fine for safety, but plan for it before relying on PG task reads.
- **Latency:** the structure mirror is on the request path (≤5 s bounded). Adding
  task dual-write on the high-frequency task-toggle path would compound this →
  J9 should consider off-request-path delivery (waitUntil/outbox).
- **No hard-delete reconciliation** (carried from J8): a hard-removed area/job
  leaves a stale PG row, never served (Blob-spine). Acceptable; revisit before
  Blob retirement (J11).

## 14. J9 readiness assessment

The structure loop is **proven correct and safe** end-to-end. J9 (task-instance/
status dual-write) is safe to **build** on the same proven pattern (best-effort,
flag-dark, Blob-authoritative, idempotent). It is **not** blocked by a defect.

However, two decisions should be made first so J9 delivers real value rather than
silent fallback: (a) how to handle legacy representational drift (accept
incremental coverage, run a normalization pass, or adjust read parity), and
(b) keep the high-frequency task-toggle mirror off the request path. Hence:

### Is J9 safe to begin? **CONDITIONAL**

- **YES** to building task dual-write on the proven, safe pattern.
- **CONDITION 1:** acknowledge that, like structure, task reads will conservatively
  fall back to Blob for legacy-shaped jobs until normalized — so the production
  read-cutover value is incremental, not immediate.
- **CONDITION 2:** design the task-toggle mirror to avoid adding request latency on
  the high-frequency field path (off-request-path or debounced).

No production changes, no schema/migration changes, and no read cutover were made.
Dev was left exactly as found (sync IN SYNC, baseline hash).
